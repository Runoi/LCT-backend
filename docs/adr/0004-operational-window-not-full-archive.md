# В БД грузим операционное окно, не весь 7.5-летний архив

Контекст: датасет содержит ~313 млн строк событий за 2019 — середину 2026, но после решения об ETL-границе ([[0003-etl-produces-timeseries-not-ml-features]]) ML-часть читает исторический архив напрямую из CSV для обучения, а не из БД бэкенда. Полная загрузка архива в PostgreSQL — самый дорогой по времени пункт плана при бюджете в 7 дней.

Решение: бэкенд грузит в PostgreSQL только операционное окно — недавнюю историю, достаточную для дашборда (`/sensors/{id}/series`, `/events`) и для сидирования эмулятора, плюс готовый `журнал_событий_пример.csv` (август 2026) как sanity-check набор. Полный исторический архив остаётся набором сырых CSV-файлов, до которых бэкенд не дотрагивается.

Почему: экспертиза оценивает работающий дашборд и правдоподобность эмуляции, а не способность обслуживать произвольные многолетние запросы по API; после переноса feature engineering на сторону ML ценность полной загрузки архива в БД бэкенда резко упала.
