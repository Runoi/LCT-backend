# ETL бэкенда даёт тайм-серии по каналам, не ML-признаки

Контекст: `BACKEND_TZ_FOR_TEAM.md` §1 исключает «feature engineering по журналу событий» из зоны бэкенда, но §3.5 того же документа требует передавать в ML Prediction Port «временной срез признаков», а `BACKEND_MASTER_PLAN.md` P0 п.3 ставит бэкенду задачу строить агрегаты/фичи по каналам — внутреннее противоречие документов. ML-часть реально пишется отдельной командой, чей конкретный вход/выход пока не согласован.

Решение (предварительное, до подтверждения ML-тиммейтом): бэкенд-ETL превращает сырой `ext-journal-*.csv` только в чистые **тайм-серии показаний по каналам** — то, что и так обязательно для `/api/v1/sensors/{id}/series` в дашборде. В ML Prediction Port передаётся **сырой временной срез показаний** за нужное окно, а не инженерные признаки (частоты переключений, скользящие окна и т.д.) — их считает сама ML-часть, как при инференсе, так и при обучении (читая историю напрямую из CSV, не через бэкенд).

Почему: резко снижает объём инженерной работы за 7 дней (не нужен отдельный feature store), совпадает с буквальной формулировкой границ в `BACKEND_TZ_FOR_TEAM.md` §1. Пересмотреть после уточнения у ML-тиммейта точного формата ожидаемого входа.
