# ML Prediction Port — простой самодельный контракт, не форма INDASTRICS

Контекст: `BACKEND_INDASTRICS_INTEGRATION.md` описывает контракт `BaseMLForecastingModel` (`fit`/`predict`/`predict_with_intervals` + скан-до-порога, даёт RUL/Health Index) — заточен под непрерывную деградацию промышленного роторного оборудования. Наш кейс (отказ датчика / инцидент) ближе к бинарной классификации с вероятностью и горизонтом, чем к тренду до порога. [[0001-backend-only-mvp-scope-with-integration-ports]] уже решил, что INDASTRICS — не основной путь.

Решение: ML Prediction Port использует простую самодельную форму — один вызов с временным срезом показаний на входе, `probability`/`prediction_window`/`risk_level`/`top_factors[]`/`recommendation` на выходе (то же, что уже требует фронтенд-контракт), без попытки заранее уложить это в форму `fit/predict/predict_with_intervals`.

Почему: не вынуждает ML-часть подгонять задачу под чужую ментальную модель ради гипотетической совместимости; если INDASTRICS позже подтвердится обязательной, адаптер-переводчик дешевле дописать поверх простого контракта, чем усложнять контракт сейчас ради пути, который уже не выбран основным.
