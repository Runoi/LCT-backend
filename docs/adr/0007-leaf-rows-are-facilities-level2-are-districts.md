# Листовые строки справочника объектов — facility, уровень 2 — district

Контекст: `справочник_объектов_диспетчер.csv` — 95 строк, 3 уровня (1 корень `district` / 16 узлов уровня 2, все `controlHouse` / 78 листьев уровня 3: 49 `controlHouse` + 29 `guardObject`, 0 «осиротевших» родителей — проверено напрямую по файлу). Документы проекта непоследовательно называют то 95, то фактическую листовую часть «объектами» — какие строки становятся `facility` для `/api/v1/facilities`, нигде явно не зафиксировано (открытый вопрос в `BACKEND_REQUIREMENTS_FROM_FRONTEND_TZ.md` §12: «реальная иерархия объектов... предположительно временная структура»). Иерархия объектов требует параметр фильтра `district=`, а модель RBAC (ADR 0002) уже вводит собственную сущность «район» как ось `scope`, изначально не привязанную к реальным данным.

Решение: 78 листовых строк (уровень 3) становятся записями `facility` (`facility_id = f"fac_{ид_объект}"`, `display_name` = `диспетчерское_название_объекта`, `facility_type` = `вид_объекта`). 16 строк уровня 2 становятся записями `district` — той же сущностью, которую уже создала модель RBAC для `scope` (`districts`/`district_facility_ids`), а не отдельной параллельной таблицей. Единственная строка уровня 1 — корень организации — отдельно не экспонируется (нет отдельного «уровня выше района» в контракте фронтенда).

Почему: использует все 95 строк осмысленно (не отбрасывая 17 нелистовых как мусор), даёт фильтру `district=` реальное наполнение, и напрямую переиспользует модель «район» из RBAC вместо параллельной несвязанной структуры — тем самым иерархия объектов и RBAC используют одну сущность, а не формально ссылаются друг на друга.
