# Методы обработки данных

## Потоковый ETL реального датасета

- `справочник_каналов_датчиков.csv` (11 485 строк, настоящий CSV-парсер — не построчный сплит, в файле встречаются переносы строк внутри кавычек) → `sensor_channels`.
- `журнал_событий_пример.csv` (169 993 строки, август 2026 — **операционное окно**, не полный архив `ext-journal-*.csv` за 2019-2026, см. `docs/adr/0004-operational-window-not-full-archive.md`) → `sensor_readings`, читается через `csv.DictReader` построчно (`src/services/event_etl.py`), батчами по 2000 строк — файл никогда не грузится в память целиком.
- Идемпотентность — маркер `etl_ingested_sources` (какой файл целиком проглочен), не подсчёт строк.
- Сентинел-значения (`01.01.1970...`, вендор-специфичные коды вроде `-100`, `255`) размечаются как `is_anomaly=True`, никогда не превращаются в правдоподобное на вид число.
- Каналы, встреченные в журнале, но отсутствующие в справочнике, не отбрасываются — создаются как orphan-канал (`sensor_type_id="unknown"`, `facility_id=None`), видимый только пользователям со scope `all_facilities`.

## Эмуляция внешних источников (`docs/adr/0005`)

- **СМВУ** — не второй ETL и не подмена реальных данных. Фоновый `replay_engine.py` держит виртуальные часы внутри операционного окна; каждый тик реплеит копии реальных показаний (`origin="historical"`) с `occurred_at=сейчас` и `origin="replay"`. При достижении конца окна — переход на начало (окно конечно, демо — нет). Управляется `REPLAY_SPEED_MULTIPLIER`/`REPLAY_TICK_SECONDS`.
- **Fixture-сценарии** (16 штук, по 4 на каждый `risk_type`) — заранее описанные хронологические последовательности реальных `sensor_type_id`, активируются по запросу (`POST /system/scenarios/{id}/activate`) поверх фонового потока, для управляемой демонстрации. Часть сценариев использует `random.Random(seed)` (явная рекомендация организаторов для сценария «пожар») — воспроизводимость обеспечивается фиксированным `seed`, не отсутствием RNG.
- **ОДС/реестр оборудования/система заявок** — полностью синтетические (реальных данных для них нет), но объём/распределение выведены из реального датасета: реестр оборудования — детерминированно из фактического состава каталога каналов (без RNG вообще); журнал ОДС и backlog заявок — объём пропорционален реальному количеству тревог по объекту, `seed`-детерминированный RNG только для конкретных временных меток/категорий внутри этого выведенного объёма.
- **Статус источников** (`GET /system/source-health`) — не имитирует живое подключение: `online/delayed/unavailable` вычисляется самим сервисом по возрасту последнего успешного тика/синка каждого провайдера относительно `FRESHNESS_BOUNDARIES`. Искусственная деградация — `POST /system/source-health/{source}/degrade`, тоже детерминированный локальный вызов, не поллинг внешней системы.

## Ленивая материализация цепочки Event → Risk → WorkOrder

Общий паттерн, не фоновый воркер: `sync_*` идемпотентно продвигает high-water-mark и коммитит батчами. `sync_events` и статус заявок вызываются в начале соответствующего `GET`-запроса; `sync_risks` — при старте приложения, потому что каждый его шаг — сетевой вызов ML-сервиса, и делать их внутри пользовательского запроса значило бы привязать время ответа API к ML.

- **`sync_events`** — сканирует `sensor_readings` с `is_alarm OR is_anomaly` за пределами последнего обработанного id, материализует по одному `Event` на показание (обычные показания в журнал не попадают — это заметные происшествия, не полный поток телеметрии, для которого уже есть `/sensors/{id}/series`).
- **`sync_risks`** — сканирует `Event` с `related_risk_id IS NULL`, группирует по датчику, вызывает ML Prediction Port **один раз на группу** (не на каждое событие), создаёт один `Risk`, простав `related_risk_id` на всю группу. Если ML-сервис отвечает ошибкой (например, `422 insufficient_data`) или недоступен, группа пропускается без прогноза, курсор всё равно сдвигается.
- **Риски по объектам** — при старте, если задан `ML_PREDICTOR_URL`: `POST /risk_map` для `incident` (72 ч) и `failure` (168 ч); каждый объект с `alert` становится `Risk` с `target_type = "facility"`, повторный старт не дублирует открытый риск той же модели.
- **Статус `WorkOrder`** — чистая функция `status_for_elapsed(created_at, now)` (кумулятивные пороги в минутах от создания), без мутируемого состояния тика — безопасна для повторного вызова. `cancelled`/`integration_error` намеренно исключены из автоматической цепочки (решение человека / реальный сбой интеграции, которой нет).

## ML Prediction Port (`docs/adr/0006`)

HTTP-граница, не Python-интерфейс внутри кодовой базы — backend и ML-модель развиваются и деплоятся независимо (`docs/adr/0001`). `HttpMLPredictor` вызывает `POST {ML_PREDICTOR_URL}/predict` с документированным контрактом (`src/services/ml_port.py::PredictionInput/PredictionResult`); без `ML_PREDICTOR_URL` backend поднимает `StubPredictor` (детерминированный, вероятность — функция реального количества alarm/anomaly в окне, не случайный шум).
