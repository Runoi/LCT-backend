# Безопасность

Документ сверяет решение с требованиями ТЗ по безопасности: §11 «Безопасность», §5 «защита данных от несанкционированного доступа», §7 (обфускация на стороне источника), §13 (интеграции только на чтение), §14 (149-ФЗ, 152-ФЗ). Для каждого пункта указано, что реализовано по-настоящему, что заменено mock-ом и на каком основании.

## Сводка

| Требование ТЗ | Статус | Как реализовано |
|---|---|---|
| Шифрование при передаче, TLS 1.2 и выше (§11) | Реализовано | Reverse-proxy nginx перед приложением, только TLS 1.2/1.3 |
| Аутентификация с интеграцией LDAP/AD (§11) | Mock | Локальные учётные записи; реальный каталог недоступен на хакатоне |
| Ролевая модель доступа, RBAC (§11) | Реализовано | Права (capability) + зона видимости (scope) на каждом эндпоинте |
| Журналирование всех действий пользователей (§11) | Реализовано, с оговорками | Журнал аудита всех изменяющих запросов и входов |
| Защита от несанкционированного доступа (§5) | Реализовано | Срок жизни сессий, выход, защита от перебора паролей |
| Интеграции только на чтение (§13) | Соблюдено | Внешние системы эмулируются локально, запросов к системам заказчика нет |
| Обфускация данных на стороне источника (§7) | Соблюдено | Датасет обезличен; backend не полагается на персональные данные |
| 149-ФЗ, 152-ФЗ (§14) | Соблюдено в рамках MVP | Персональные данные — только логины демо-пользователей |

## TLS 1.2 и выше

- `docker compose up` поднимает сервис `proxy` (nginx) перед приложением. Он принимает только HTTPS с протоколами TLS 1.2 и TLS 1.3; попытка подключиться по TLS 1.0 или 1.1 отклоняется самим сервером (алерт `protocol version`).
- API доступен по `https://localhost:8443` (порт меняется переменной `HTTPS_PORT`). Порт `HTTP_PORT` (по умолчанию 8080) отвечает только перенаправлением 301 на HTTPS.
- Порты приложения (8000) и PostgreSQL (5432) наружу не публикуются: к ним можно обратиться только из внутренней сети compose, то есть только через TLS-прокси.
- Сертификат самоподписанный и создаётся автоматически при первом запуске (том `proxy_certs`), ручных шагов нет. Браузер покажет предупреждение о недоверенном сертификате, `curl` нужно запускать с `-k`. Для эксплуатации сертификат заменяется на выпущенный доверенным УЦ заказчика — достаточно положить `server.crt`/`server.key` в том сертификатов.
- Прокси перезаписывает заголовок `X-Forwarded-For` реальным адресом клиента, поэтому подменить IP в журнале аудита через заголовок нельзя.

## Аутентификация и LDAP/AD

- Интеграция с корпоративным каталогом LDAP/AD — **mock**. Организаторы подтвердили, что реальная интеграция с LDAP/TLS/PostgreSQL заказчика не требуется и невозможна, mock достаточен (`info/QA_ORGANIZERS_CLARIFICATIONS.md`, §8). Тестового контура AD на хакатоне нет.
- Пользователи хранятся локально; пароли — только в виде хеша PBKDF2-HMAC-SHA256 (200 000 итераций, случайная соль), сравнение за постоянное время.
- Вход (`POST /api/v1/auth/login`) выдаёт непрозрачный серверный токен. Замена mock на реальный LDAP/AD затрагивает только проверку пароля; модель прав и зон видимости от способа аутентификации не зависит.

### Срок жизни сессии и выход

- Каждая сессия действует `SESSION_TTL_MINUTES` минут (по умолчанию 480 — одна смена). Истёкший токен отклоняется с `401 SESSION_EXPIRED`. Сессии, созданные до появления срока действия, при миграции получили срок `created_at + 480 минут` и не остались бессрочными.
- `POST /api/v1/auth/logout` немедленно отзывает текущий токен; другие сессии того же пользователя не затрагиваются.

### Защита от перебора паролей

- После `LOGIN_MAX_FAILURES_PER_USERNAME` (5) неудачных попыток для одного логина или `LOGIN_MAX_FAILURES_PER_IP` (20) с одного IP в окне `LOGIN_FAILURE_WINDOW_SECONDS` (900 с) вход блокируется: ответ `429 TOO_MANY_REQUESTS`, `retryable: true`, в `details.retry_after_seconds` — время до разблокировки.
- Во время блокировки не пускает и верный пароль. Отклонённые блокировкой попытки не продлевают её.
- Успешный вход обнуляет счётчик логина; счётчик IP не обнуляется, чтобы одна рабочая учётная запись не сбрасывала попытки подбора чужих паролей с того же адреса.
- Ответ не раскрывает, существует ли логин: неизвестный логин получает тот же 401 и так же блокируется.
- Лимит на IP выше лимита на логин, чтобы офис за одним NAT не блокировался из-за нескольких опечаток коллег.

## RBAC

- Модель — права (capability) плюс зона видимости (scope), без привязки к названию роли (`docs/adr/0002-capability-scope-rbac-with-district-level.md`). Фильтрация выполняется на backend в каждом эндпоинте, а не скрытием элементов на фронтенде.
- Зона видимости: все объекты либо назначенные объекты и районы. Запрос к объекту вне зоны — `403 FACILITY_ACCESS_DENIED`, списки возвращают только видимые объекты.
- Управление эмуляцией (активация сценариев, деградация источников) требует права `system.manage`, а активация сценария дополнительно проверяет зону видимости по объекту. Чтение статуса источников и списка сценариев доступно всем вошедшим.
- Журнал аудита читается только с правом `audit.read`.
- Демо-пользователи: `manager` — все права, включая `system.manage` и `audit.read`, все объекты; `dispatcher` — `facility.read.assigned`, `sensor.read`, `risk.read`, `risk.acknowledge`, `work_order.read`, `work_order.create_draft`, объекты `fac_5122` и `fac_5339`.

## Журнал аудита

- Таблица `audit_log` хранит: время, пользователя (для неудачного входа — введённый логин), действие вида `POST /api/v1/risks/{risk_id}/acknowledge`, тип и id целевого объекта, результат (`success`, `denied`, `failure`), HTTP-код, IP клиента, `trace_id` и при необходимости уточнения (например, объект активированного сценария или причина `locked_out`).
- Записывается каждый изменяющий запрос к API (POST/PUT/PATCH/DELETE), включая отказы по правам, неудачные входы, блокировки и выход. Новые изменяющие эндпоинты попадают в журнал автоматически — запись делает общий middleware, а не каждый эндпоинт отдельно.
- `trace_id` один и тот же в заголовке ответа `X-Trace-Id`, в теле ошибки и в записи журнала — по нему любой ответ находится в журнале.
- Журнал только пополняется: API изменения или удаления записей нет. Просмотр — `GET /api/v1/audit` с фильтрами по пользователю, действию и периоду и курсорной пагинацией.
- Пароли, токены, тела запросов и заголовки в журнал не записываются.
- Сбой записи в журнал логируется и не ломает ответ пользователю.

### Осознанные ограничения журнала

- **Запросы на чтение (GET) не журналируются.** Дашборды опрашивают API непрерывно; журнал утонул бы в чтениях, а поиск значимых действий стал бы бесполезным. Все изменения данных, входы, выходы и отказы журналируются полностью.
- **Необработанные ошибки 500 не журналируются.** Они перехватываются внешним слоем Starlette, который находится снаружи middleware журнала. Обработанные ошибки (4xx и доменные ошибки) журналируются.

## Интеграции только на чтение

Все внешние системы (СМВУ, журнал ОДС, реестр оборудования, система заявок) эмулируются внутри backend (`docs/adr/0005`). Никаких запросов на запись — как и на чтение — в системы заказчика не выполняется; реальные интеграции организаторы закрыли по соображениям безопасности. Единственный исходящий вызов — к ML-сервису команды по `ML_PREDICTOR_URL`, и он не является системой заказчика.

## Обфускация данных, 149-ФЗ и 152-ФЗ

- Выданный датасет уже обезличен на стороне источника: идентификаторы каналов, типы датчиков, значения и диспетчерские названия объектов, без сведений о людях. Backend не полагается на наличие персональных данных в открытом виде.
- Единственные персональные данные в системе — логины и отображаемые имена демо-пользователей. Пароли хранятся только в виде хеша.
- Доступ к данным ограничен ролевой моделью, передача защищена TLS, действия пользователей журналируются — это базовые меры защиты информации по 149-ФЗ. При подключении реальных учётных записей из AD обработка их данных (ФИО, логин) подпадает под 152-ФЗ и оформляется по регламентам заказчика.

## Справочник `/api/v1/config` без авторизации

`GET /api/v1/config` отдаётся без токена намеренно. Он содержит только справочники интерфейса (типы датчиков, уровни риска, причины отклонения, типы работ, границы свежести данных) — ни объектов, ни показаний, ни пользователей. Фронтенду эти справочники нужны до входа, например для экрана логина и подписей. Остальные эндпоинты `/api/v1/*`, кроме `POST /auth/login`, требуют токен. Без токена также доступны `/health` (проверка живости) и описание API (`/docs`, `/openapi.json`) — в них нет данных.

## Как проверить

```
docker compose up --build
curl -k https://localhost:8443/health
curl -k -X POST https://localhost:8443/api/v1/auth/login -H "content-type: application/json" -d '{"username":"manager","password":"manager123"}'
curl -k https://localhost:8443/api/v1/audit -H "Authorization: Bearer <token>"
```

Отказ устаревших протоколов проверяется изнутри контейнера прокси:

```
docker compose exec proxy openssl s_client -connect 127.0.0.1:443 -tls1_1 -cipher DEFAULT@SECLEVEL=0
```

Ожидаемый результат — ошибка `alert protocol version` от сервера.
