# Требования к бэкенду

Сервис прогнозирования инцидентов и управления ремонтными работами инженерных коллекторов Москвы.

Документ выделяет из ТЗ («8. ДЖКХ_ТЗ.pdf») требования, относящиеся к серверной части / бэкенду: обработка данных, прогнозная модель, API, интеграции, производительность, надёжность, безопасность и архитектура. Требования к UI/UX, презентации и сдаче решения — вне рамок этого документа.

## 0. Уточнение организаторов: реальных интеграций на хакатоне нет

По ответу организаторов на вопрос об интеграции с системой учёта заявок:

- Система учёта заявок заказчика — собственный **help desk на Django**. Реальная интеграция с ней невозможна по соображениям безопасности.
- Это относится ко **всем** внешним источникам из раздела 3/13 (СМВУ, журналы ОДС, реестр оборудования, система учёта заявок) — ни один из них реально не предоставляется участникам.
- Все внешние взаимодействия должны быть реализованы через **шаблоны (mock REST API) и эмуляцию событий**, а не через реальные подключения.
- Эмулируемые данные обязаны выглядеть **адекватно и правдоподобно** (реалистичные значения, паттерны, временные ряды), а не быть случайными числами — это будет оцениваться при экспертизе (см. раздел 17 и 18 общего ТЗ, критерий «проверка прогнозирования / оценка достоверности»).

**Следствие для архитектуры бэкенда**: слой интеграции с внешними источниками должен быть спроектирован как заменяемый адаптер (аналогично mock/http adapter на фронтенде) — с самого начала реализуется mock-провайдер данных СМВУ/ОДС/реестра/заявок, а не «заглушка на скорую руку», потому что это единственный источник данных на весь хакатон.

## 1. Общие функциональные обязанности бэкенда

Сервис (бэкенд):

- анализирует исторические и текущие данные мониторинга;
- обрабатывает информацию из журналов диспетчерской службы (ОДС);
- работает с реестром оборудования;
- рассчитывает и предоставляет прогнозы инцидентов с указанием вероятности и временного горизонта;
- осуществляет предиктивное моделирование инцидентов на основе исторических данных;
- интегрируется с существующими системами мониторинга (СМВУ) для получения данных.

Сервис НЕ должен:

- замещать работу диспетчеров (принятие решения остаётся за человеком);
- принимать окончательные решения об инцидентах;
- управлять инженерным оборудованием напрямую;
- инициировать/проводить ремонтные работы.

## 2. Прогнозирование инцидентов

- Анализ данных с датчиков (контактные, объёмные, температурные, дымовые, газовые) для выявления потенциальных рисков инцидентов.
- Расчёт вероятности инцидента с горизонтом прогнозирования **не менее 24 часов**.
- Определение локации оборудования, подверженного риску (привязка к объекту/тегу в дереве объектов).
- Классификация типов прогнозируемых инцидентов (пожар, подтопление, несанкционированный доступ, отказ датчика/оборудования и т.д.).

### Сценарный анализ

- Анализ сценариев инцидентов (пожар, проникновение, подтопление) на основе исторических данных и паттернов.
- Формирование превентивных уведомлений об инцидентах на основе прогнозных моделей.
- Формирование рекомендаций по техническому обслуживанию и ремонту на основе анализа состояния оборудования (в т.ч. прогноз отказа датчика).

### Метрики качества модели

- Целевые показатели **Precision** и **Recall** определяются на этапе проектирования, исходя из качества предоставленных данных — модель/пайплайн должны позволять их измерение и отслеживание (в т.ч. на основе фидбэка диспетчера — см. п. 6).

## 3. Работа с данными

### 3.1 Источники данных (внутренние)

| Источник | Содержание | Способ получения (по ТЗ) | Доступность на хакатоне |
|---|---|---|---|
| СМВУ (система мониторинга) | показания датчиков: контактные, объёмные, температурные, дымовые, газовые | интеграция near real-time (API/очередь сообщений), режим **read-only** | недоступна — только mock/эмуляция |
| Журналы ОДС | записи о срабатываниях, история инцидентов | загрузка через API; глубина истории — **не менее 12 лет** | недоступна — только mock/эмуляция |
| Реестр оборудования | строительные конструкции (люки, вентшахты, камеры), электрооборудование (насосы, вентиляторы), датчики | цифровой формат, синхронизация из учётных систем заказчика | недоступна — только mock/эмуляция |
| Система учёта заявок | статусы заявок на ремонтные работы | интеграция (получение статусов) | недоступна — собственный Django help desk заказчика, интеграция закрыта по безопасности; только mock REST API |

Датасет, реально выданный участникам (95 объектов, 11 485 актуальных каналов из 12 627 исторических, журнал сработок и т.д. — см. `BACKEND_REQUIREMENTS_FROM_FRONTEND_TZ.md`, разделы 6.2 и 12), — это статичный экспорт, а не живое подключение к перечисленным системам; потоковый и API-доступ к ним нужно проектировать как будущую интеграцию, реализуя её на хакатоне через эмулятор.

### 3.2 Источники данных (внешние)

- Метеослужбы: температура, влажность, осадки, атмосферное давление — интеграция через открытые API.
- Нормативная документация (РТЭК) — используется как справочная основа правил/регламентов.

### 3.3 Входные форматы и обмен данными

- Исторические данные: импорт из **CSV/XLSX**.
- Потоковые данные СМВУ: **API / очередь сообщений**.
- Журналы ОДС: загрузка через **API**.
- Программный обмен: **JSON, XML**.
- Геоданные: **GeoJSON, WKT**.
- СУБД: подключение к **PostgreSQL 12+** (или иной СУБД инфраструктуры заказчика).

### 3.4 Обработка и хранение

- Все входящие данные должны проходить **обфускацию (обезличивание) на стороне источника** — бэкенд обязан поддерживать работу с уже обезличенными данными (учитывать при проектировании схемы).
- Данные разделяются на:
  - **оперативный контур** (текущие данные для inference/near real-time обработки);
  - **архив** (историческая глубина, включая ≥12 лет журналов ОДС);
  - **аналитические витрины** (агрегаты для отчётности/дашбордов).
- Интеграция с внутренними системами заказчика — только в режиме **read-only**.

## 4. API и интеграции

- Предоставление **REST API** для получения данных внешними системами/фронтендом.
- Форматы обмена через API: **JSON, XML**.
- Получение данных о состоянии оборудования из систем мониторинга — режим чтения (read-only).
- Автоматизированная **синхронизация реестра оборудования** из учётных систем заказчика.
- Интеграция с системой учёта заявок для получения статусов ремонтных работ.
- Поддержка формирования черновиков заявок на ремонт на основе рекомендаций системы (дополнительный модуль, по согласованию с заказчиком).
- Формирование аналитических отчётов для выгрузки в **PDF, XLSX** (дополнительное требование).

## 5. Производительность

- Время формирования прогноза (**inference**) для одного объекта: **не более 300 секунд** (в разделе 9 указано ориентировочно "не более 5 минут" — итоговое нормативное значение 300 сек, раздел 11).
- Обработка потоковых данных: близко к реальному времени, задержка **не более 300 секунд**.
- Одновременная работа **не менее 20 пользователей** без деградации производительности.
- Отсутствие деградации производительности при параллельной работе всех пользователей системы.

## 6. Журнал прогнозов и обратная связь (для дообучения)

Бэкенд должен обеспечивать хранение и обработку следующего цикла (см. пользовательские сценарии, п. 12 ТЗ):

1. Формирование прогноза (вероятность, горизонт, локация, тип инцидента).
2. Публикация уведомления/предупреждения (в т.ч. критические инциденты — в режиме реального времени).
3. Фиксация решения диспетчера (например: «выезд бригады», «ложное срабатывание», «мониторинг ситуации») с указанием причины из справочника.
4. Сохранение решения в журнале для последующего анализа и **дообучения модели**.

Соответствующий модуль дообучения прогнозных моделей на новых данных — часть дополнительного функционала (по согласованию с заказчиком).

## 7. Надёжность

- Доступность системы — в соответствии с регламентом эксплуатации ИС заказчика.
- Автоматическое резервное копирование данных.
- Время восстановления работоспособности после сбоя — **не более 4 часов**.

## 8. Безопасность

- Шифрование данных при передаче — **TLS 1.2 и выше**.
- Аутентификация пользователей с поддержкой интеграции с корпоративной службой каталогов (**LDAP/AD**).
- Разграничение прав доступа на основе ролевой модели (**RBAC**).
- Журналирование всех действий пользователей в системе (аудит-лог).
- Данные должны поступать уже обфусцированными от источника; бэкенду нельзя полагаться на наличие персональных/чувствительных данных в открытом виде.
- Соответствие требованиям 149-ФЗ («Об информации...») и 152-ФЗ («О персональных данных»).

## 9. Совместимость и инфраструктура

- Серверная часть: **Linux**.
- СУБД: **PostgreSQL 12 и выше**.
- Взаимодействие с БД через **SQL**.

## 10. Требования к архитектуре и документации решения

- Решение реализуется как **отдельный сервис**, способный быть самостоятельной информационной системой либо компонентом другой системы; количество внешних интеграций должно соответствовать целям задачи (не избыточно).
- Все используемые методы должны быть документированы; должен быть перечень всех библиотек/компонентов.
- Сложные технические/логические участки — сопровождаются комментариями в коде.
- Обязательна сопроводительная документация, описывающая:
  - используемые методы обработки данных;
  - условия и ограничения решения;
  - инструкции по сборке/установке/компиляции;
  - функциональную и компонентную архитектуру.
- Исходный код передаётся в открытом, неоткомпилированном виде, без обфускации кода.

## 12. Приложение: фактический состав выданного датасета (`S:\ЛЦТХакатон\dataset`, зафиксировано 2026-09-19)

Раздел добавлен как справочный слепок реально выданных файлов — **не заменяет** требования выше, а фиксирует, с чем конкретно предстоит работать data/backend-части, чтобы не потерять эти наблюдения по ходу командной работы (формат может отличаться от того, что ожидают ML-модели сокомандников — стоит сверяться с этим разделом при спорах о схеме).

### 12.1 Состав файлов

| Файл | Размер | Строк | Назначение |
|---|---|---|---|
| `справочник_объектов_диспетчер.csv` | 5 КБ | 95 | реестр объектов, 3-уровневая иерархия |
| `справочник_каналов_датчиков.csv` | 1.2 МБ | 11 494 | реестр каналов датчиков |
| `журнал_событий_пример.csv` | 9.7 МБ | 169 993 | отдельно подготовленная **выборка-пример** событий (только август 2026, позже последнего годового архива) |
| `ext-journal-2019.csv` … `ext-journal-2026.csv` | 1.2–2.7 ГБ каждый (8 файлов) | ~313.5 млн суммарно | полный исторический журнал событий по годам (2019 → 30.06.2026) |

Общий объём годовых архивов — порядка 15.5 ГБ текста, десятки миллионов строк на файл (от ~21 млн в 2019 до ~55.5 млн в 2025) — обрабатывать потоково, не грузить файл целиком в память.

### 12.2 Схема `справочник_объектов_диспетчер.csv`

Колонки: `ид_объект, иерархия_уровень, родитель, вид_объекта, диспетчерское_название_объекта`.

- Уровень 1 — один корневой узел (`district`, «Район по эксплуатации»).
- Уровень 2 — 16 узлов вида `controlHouse`.
- Уровень 3 — 78 листовых узлов: 65 × `controlHouse`, 29 × `guardObject` (смешаны, не строго типизированы по позиции в дереве).

### 12.3 Схема `справочник_каналов_датчиков.csv`

Колонки: `ид_канала_данных, тип_инж_системы, тип_датчика, тег_инженерной_системы, название_датчика`.

Распределение по `тип_инж_системы` (6 значений): Пожарная охрана (5701), Диспетчерский контроль (2364), Охранная подсистема (2211), Температурная подсистема (600), Газовая охрана (529), Диагностическая подсистема (80).

Распределение по `тип_датчика` (19 значений, по убыванию): датчик дыма, состояние фазы, КД Дверь, датчик движения, переключатель, состояние УИР-Р, датчик температуры, газовый датчик, тепловой датчик, КД АВ, состояние вентилятора, состояние насоса, ручной извещатель, ИБП, КД Люк, состояние охраны, стекло, датчик затопления, 9-секционный люк.

### 12.4 Схема журналов событий (`журнал_событий_пример.csv` и `ext-journal-*.csv`)

Колонки: `ид_события, ид_канала_данных, дата, время, тревожное, значение_датчика`.

- `тревожное` — булево, но кодировка **не унифицирована между файлами**: в `журнал_событий_пример.csv` встречается `true`/`false`, в годовых `ext-journal-*.csv` — `t`/`f`. Парсер должен поддерживать оба варианта.
- `значение_датчика` — нетипизированная текстовая колонка, содержит вперемешку:
  - числа («0.01», «28», «0.16»);
  - категориальные состояния («Норма», «Включен», «Не замкнут», «На охране», «Снято с охраны», «Работают все насосы в АНС», «Много неисправных устройств»);
  - «мусорные» значения вроде `01.01.1970 03:00:00` / `01.01.1970 03:00:01` — похоже на дефолт unix-эпохи при сбое датчика или парсера источника; такие значения нужно уметь отличать от валидных показаний и метить как аномалию, а не как «Норма».
  - Тип значения (`numeric` vs `categorical`) в самом журнале не указан — определяется только по `тип_датчика` из справочника каналов (см. 12.3), сопоставляя `ид_канала_данных`.
- Заголовки CSV оформлены непоследовательно: в справочниках и в `журнал_событий_пример.csv` — в кавычках (`"ид_события","ид_канала_данных",...`), в `ext-journal-*.csv` — без кавычек. Нужен единый устойчивый CSV-парсер, а не жёсткий сплит по строке заголовка.
- `ext-journal-2026.csv` обрывается на 30.06.2026, при этом `журнал_событий_пример.csv` содержит данные за август 2026 — то есть это не хвост того же архива, а отдельно подготовленный демонстрационный срез.

### 12.5 Соответствие ранее задокументированным оценкам

- 95 объектов и глубина истории по годам подтверждают цифры, упомянутые в `BACKEND_REQUIREMENTS_FROM_FRONTEND_TZ.md` (раздел 6.2 и 12) — 95 объектов сходится точно; 11 494 канала в справочнике близко к упомянутым там «11 485 актуальных каналов» (возможно, версия справочника чуть отличается).
- Фактическая глубина архива — 2019 – середина 2026 (~7.5 лет), что несколько меньше заявленных в общем ТЗ «не менее 12 лет»; при проектировании ETL/модели стоит явно закладывать работу с тем, что реально выдано, а не с тем, что заявлено как норматив.
- Внешний метеоисточник, упомянутый в общем ТЗ (раздел 13), на диске представлен отдельно от `dataset/` — файлом `weather_msk_2019_raw.csv` в корне `S:\ЛЦТХакатон` (не внутри `dataset/`), его схему стоит сверять отдельно при интеграции с прогнозной моделью.
