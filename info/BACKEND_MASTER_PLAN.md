## 1. Рамки проекта

**Задача**: сервис предиктивной аналитики для прогнозирования инцидентов и отказов датчиков инженерных коллекторов Москвы + аналитическая поддержка диспетчера (ОДС), сдаётся как хакатон-MVP, не промышленное внедрение.

**Правила игры хакатона** (сведено из QA):

| Ограничение | Факт |
|---|---|
| Вычислительные ресурсы | не предоставляются вообще (в т.ч. GPU), всё разворачивается командой самостоятельно |
| Реальные интеграции | невозможны по безопасности — СМВУ/ОДС/реестр/заявки/LDAP/AD только mock |
| Тестовый период/лидерборд | нет единого закрытого теста — оценка вручную экспертами на своих стендах |
| Стек технологий | свободный |
| MVP | = все пункты ТЗ, помеченные обязательными; отступления допустимы только с письменным обоснованием |
| Формат сдачи | пакет «распаковать и запустить» + инструкция + документация; демо-стенд и видео — необязательная, но рекомендованная страховка |
| Дедлайн | жёсткий формальный критерий, важнее части содержательных недоработок |
| Дальнейшая доработка | топ-10 получает фидбэк и шанс доработать перед финалом |

### 2.1 Собственный погодный датасет (`weather_msk_2019_raw.csv`)

Полезен и явно востребован сценарием «подтопление» из ТЗ. Сейчас покрывает только 2019 год (наименее ценный по объёму событий). План: расширить на 2020–2026 (приоритет — 2021, 2022, 2024, 2025 как годы с максимальным объёмом событий в журнале), добавить поле влажности (отсутствует, но названо в ТЗ), явно зафиксировать таймзону (МСК, как и в журнале событий).

## 3. Домен: сущности, иерархия, роли

Иерархия (сведено из фронтенд-ТЗ и фактического датасета):

```
Объект (facility, 95 шт.)
  -> Здание/сооружение (опционально)
    -> Коллектор
      -> Участок/зона
        -> Оборудование (опционально для MVP)
          -> Датчик/канал (11 485+ каналов, 19 типов, 6 инженерных систем)
```

### 3.1 Ролевая модель — требует сведения (открыто)

Два независимых источника дают разные модели:

- **Фронтенд-ТЗ (MVP)**: 2 роли — Руководитель (все объекты) / Диспетчер объекта (только назначенные).
- **Реальная модель заказчика (QA §5)**: 3 уровня — Техник (1 объект) → Диспетчер района (группа объектов) → Центральная диспетчерская/ОДС (всё, ~100 тыс. датчиков); плюс предложенная организатором отдельная роль «группа реагирования» (подтверждение тревог на месте).

**Решение для backend (черновое, требует подтверждения с фронтенд-командой)**: строить permissions-модель не как фиксированные роли, а как capability-строки с параметризуемым `scope` (см. `facility.read.all` / `facility.read.assigned` в фронтенд-контракте) — тогда 3-уровневая модель заказчика реализуется через тот же `scope`, просто с промежуточным уровнем «район» как группой `facility_ids`, без изменения контракта. Роль «группа реагирования» — в backlog (P1/P2), не blocking для MVP.

## 4. Целевая переменная и прогнозирование

Два независимых, отдельно оцениваемых направления (равный приоритет, можно закрыть одно или оба):

1. **Отказ датчика** — нет формального кода события; отказ определяется вендор-специфичными сентинел-значениями или выходом за диапазон.
2. **Инцидент** (пожар/подтопление/НСД — примеры из ТЗ, не обязательный список) — ground truth отсутствует полностью, положительный класс синтезируется эвристиками (последовательности срабатываний, логические домены датчиков).

### 4.1 Решения, которые нужно принять и обосновать в пояснительной записке (организаторы сознательно оставили их открытыми)

| Развилка | Комментарий |
|---|---|
| Уровень агрегации «отказа» в дереве объектов | один канал сам по себе, или вся цепочка (питание/контроллер/связь)? Организаторы сами не знают ответа. |
| Горизонт прогноза | 24 часа — ориентир по умолчанию, не жёсткое требование; допустимы 1ч/6ч/иное с обоснованием |
| Единица Precision/Recall | по каналу или по инциденту (1 отказ шлейфа из 75 каналов = 1 или 75 событий?) — выбор команды |
| Целевые Precision/Recall (0.7/0.5) | плановые, не жёсткие — можно снижать с обоснованием |
| Включать ли 2021 год в обучение | рекомендация организаторов — исключить как аномалию (миграция системы мониторинга) |

### 4.2 Кандидатные направления моделирования

- Классические 4 сценария ТЗ: отказ датчика, пожар, подтопление, НСД.
- **Новый сценарий, подсказанный организатором (нет в самом ТЗ)**: сетевое распространение подтопления по гидравлическому уклону между связанными коллекторами — протечка в одном коллекторе без локальной тревоги может проявляться как аномальный флаппинг (частое вкл/выкл) насоса в соседнем, гидравлически связанном коллекторе. Требует графовой модели связности участков, а не по-канального анализа. Отмечено организаторами как удачная идея — стоит рассмотреть всерьёз.
- Логические домены датчиков (группировка 2–3 близких каналов) как техника снижения ложных срабатываний — общая для всех направлений.

### 4.3 Открытый вопрос: платформа INDASTRICS

Не решено (см. `BACKEND_INDASTRICS_INTEGRATION.md` §7), является ли INDASTRICS обязательной средой исполнения для этого кейса или общим шаблоном другого трека. Если она обязательна — ML-часть реализуется как `BaseMLForecastingModel`-плагин (`fit`/`predict`/`predict_with_intervals`, механизм скан-до-порога хорошо ложится на пару вероятность/горизонт). Если нет — ML-модель реализуется в обычном виде (любой стек, без ограничений). **Требует уточнения у организаторов до начала реализации ML-инфраструктуры.**

## 5. Архитектура backend (черновая, с открытыми развилками)

```
                     ┌──────────────────────────┐
Фронтенд (дашборд) ──┤   /api/v1/* (REST, JSON)  │  ← контракт зафиксирован во
                     │   наш backend-сервис      │    frontend-ТЗ, см. §6
                     └───────────┬──────────────┘
                                 │
                 ┌───────────────┴────────────────┐
                 │                                  │
     ┌───────────▼───────────┐         ┌───────────▼────────────┐
     │  ETL / feature store    │         │  Модуль эмуляции        │
     │  (ext-journal-*.csv →   │         │  внешних источников      │
     │  агрегаты по каналам/   │         │  (СМВУ, ОДС, реестр,     │
     │  объектам, признаки)    │         │  система заявок)         │
     └───────────┬───────────┘         └───────────┬────────────┘
                 │                                  │
     ┌───────────▼───────────────────────────────────▼────────────┐
     │   ML-модуль: прогноз отказа датчика / прогноз инцидента      │
     │   (возможно как INDASTRICS ML-плагин — см. §4.3, не решено)  │
     └───────────────────────────────────────────────────────────┘
```

Ключевой момент: **модуль эмуляции внешних источников — обязательная часть основной архитектуры**, а не заглушка на скорую руку (см. `BACKEND_REQUIREMENTS.md` §0) — это единственный источник «внешних» данных на весь хакатон, и организаторы прямо оценивают правдоподобность этой эмуляции.

## 6. API-контракт с фронтендом (сведено, детали — в `BACKEND_REQUIREMENTS_FROM_FRONTEND_TZ.md`)

- `/api/v1/me`, `/api/v1/facilities[/…]`, `/api/v1/sensors[/…]`, `/api/v1/risks[/…]`, `/api/v1/events`, `/api/v1/work-orders`, `/api/v1/system/source-health`.
- JSON envelope с cursor pagination, ISO 8601, snake_case enum, GeoJSON для геометрии.
- Optimistic concurrency (`expected_version` → 409) на решениях по прогнозу.
- Live updates: polling 30–60 c для MVP, SSE/WebSocket — P1.
- Коды ошибок 400/401/403/404/409/422/429/500/503 со структурой `{error: {code, message, trace_id, details, retryable}}`.
- **Геоданные — решено окончательно (QA §12): реальных координат не будет, схематическая карта разрешена и рекомендована с самого начала.** Формат — GeoJSON с условными/сгенерированными координатами либо нормализованные `x,y` для плана.
- Собственный REST API платформы INDASTRICS (`/api/calculate`, `/api/diagnose`, `/api/reliability/calculate`) **не совпадает по форме** с этим контрактом — открытый вопрос §4.3/§7 `BACKEND_INDASTRICS_INTEGRATION.md`.

## 8. Дорожная карта (P0 → P2)

### P0 — обязательный минимум (MVP)

1. ✅ Готово (2026-09-22): обновлённый справочник каналов перекачан и проверен, связь канал↔объект валидна на 100% строк.
2. Спроектировать схему БД под иерархию объект→здание→коллектор→участок→датчик (настраиваемая глубина, не хардкод).
3. Построить потоковый ETL из `ext-journal-*.csv` (313+ млн строк) в агрегаты/фичи по каналам — без загрузки файлов целиком в память.
4. Явно решить и задокументировать: уровень агрегации отказа, горизонт прогноза, единицу Precision/Recall, включение/исключение 2021 года (см. §4.1).
5. Выбрать 1–2 направления прогнозирования (отказ датчика и/или конкретный тип инцидента) — не пытаться закрыть все 4 сразу.
6. Реализовать модуль эмуляции внешних источников (СМВУ near-real-time поток, ОДС, реестр, система заявок) с правдоподобными, а не случайными данными.
7. Реализовать `/api/v1/*` согласно фронтенд-контракту (auth/me, facilities, sensors+series, risks+decisions, events, work-orders, source-health), со схематическими геоданными.
8. Базовая ML-модель для выбранного направления + карточка прогноза (факторы риска, объяснение, рекомендация) — формат карточки не регламентирован, разрабатывается командой.
9. RBAC/permissions-слой поверх capability-модели (§3.1).
10. Собрать сдаваемый пакет: код + инструкция по развёртыванию + документация (архитектура, методы обработки данных, ограничения).

### P1 — после MVP, если остаётся время

- Расширение погодного датасета на 2020–2026 (§2.1).
- Сетевая модель распространения подтопления между коллекторами (§4.2).
- SSE/WebSocket вместо polling.
- Техническая возможность дообучения модели (не обязателен сам процесс).
- Уточнение и, если потребуется, интеграция с INDASTRICS как ML-плагин (§4.3) — после получения ответа от организаторов.
- Публичный демо-стенд + видео-презентация как страховка сдачи.
- Роль «группа реагирования» отдельно от диспетчера.

### P2 — по остатку времени/ресурсов

- Расширенная аналитика, сезонные/календарные факторы риска в явном виде.
- Дополнительные каналы уведомлений (push/email/Telegram), эскалации.
- Блокировка карточки инцидента за первым открывшим пользователем.

## 10. Ключевые риски

| Риск | Смягчение |
|---|---|
| Опоздание со сдачей пакета (формальная дисквалификация) | сдавать заранее, не в последний момент; резервный публичный демо-стенд |
