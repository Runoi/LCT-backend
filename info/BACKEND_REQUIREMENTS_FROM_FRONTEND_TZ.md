# Требования к бэкенду, вытекающие из ТЗ на UX/UI и frontend

Источник: `ТЗ_UX_UI_frontend_Москоллектор_для_согласования.docx` (версия 1.0, 17.09.2026).

Сам документ — про frontend и прямо заявляет, что backend вне его границ (см. раздел 2.2 исходного файла). Но раздел 17 «Данные, которые frontend должен получать от backend» и смежные разделы (роли, авторизация, ошибки, конкурентность, live-updates) фактически являются **контрактом**, который backend обязан реализовать, чтобы frontend мог просто заменить mock-adapter на http-adapter без переписывания UI. Этот файл вычленяет и систематизирует именно эти требования.

Это дополняет [BACKEND_REQUIREMENTS.md](BACKEND_REQUIREMENTS.md) (требования из основного отраслевого ТЗ) — там про прогнозную модель и обработку данных СМВУ/ОДС, здесь — про API-контракт, авторизацию и формат ответов, которые нужны именно для веб-интерфейса.

## 1. Общий принцип

- Frontend строится на едином API adapter; после подключения backend экраны не должны переписываться — значит backend обязан строго соответствовать контракту из раздела 17 исходного документа (эндпоинты, формы ответов, коды ошибок).
- Frontend может скрывать недоступные элементы UI, но это **не защита данных**. Именно backend обязан:
  - фильтровать объекты по правам пользователя на каждом запросе;
  - запрещать доступ по прямому URL/ID к чужим объектам (403, без утечки названия/данных объекта в ответе);
  - не полагаться на клиентскую проверку ролей.

## 2. Аутентификация

Production-флоу, который должен поддержать backend:

1. Внешняя система авторизации аутентифицирует пользователя (SSO/LDAP/AD — см. общий ТЗ).
2. `GET /api/v1/me` — backend возвращает роль, permissions и доступные facility ID.
3. Frontend на основе ответа выбирает стартовый маршрут (руководитель → карта города; диспетчер с одним объектом → сразу на объект; диспетчер с несколькими — список только назначенных).

Обязательные сценарии, которые backend должен корректно поддерживать через коды ошибок/состояние сессии:

- истечение сессии (401);
- пользователь без доступных объектов;
- роль не сконфигурирована на сервере;
- прямой URL недоступного объекта → 403;
- отзыв прав в процессе активной сессии (сервер должен инвалидировать доступ немедленно, не дожидаясь истечения токена).

## 3. Модель прав доступа (RBAC / capabilities)

Frontend не должен зашивать `role === 'manager'` — вместо этого backend отдаёт явный список **permissions** для текущего пользователя. Обязательный набор capability-строк:

```
facility.read.all
facility.read.assigned
sensor.read
risk.read
risk.acknowledge
risk.resolve
work_order.read
work_order.create_draft
work_order.submit
analytics.read.summary
analytics.read.technical
report.export
```

Требования к backend:

- `GET /api/v1/me` возвращает `role`, `permissions[]`, `scope` (см. ниже), `timezone`, `locale`.
- `scope.type` — `all_facilities` (руководитель) или `assigned_facilities` с явным списком `facility_ids` (диспетчер).
- Любой список/деталь сущности должен быть отфильтрован backend согласно `scope` и `permissions` — включая поиск, автодополнение и агрегаты (диспетчер не должен получить косвенно данные чужих объектов через общегородскую статистику).

Роли MVP: **Руководитель**, **Диспетчер объекта** (могут быть назначены на 1+ объектов — уточнить у продукта, см. раздел вопросов). Роли P1/P2 (Инженер ТО, Аналитик/ML, Наблюдатель, Администратор) — за пределами MVP, но модель permissions должна быть расширяемой под них без изменения контракта.

## 4. Общие правила формата ответов API

- Транспорт: JSON over HTTPS, версия API в пути — `/api/v1`.
- Идентификаторы — непрозрачные строки (`fac_104`, `sensor_01842`, `risk_01J104`), не вычисляемые на клиенте.
- Время — ISO 8601 с offset (пример: `2026-09-17T14:35:00+03:00`).
- Вероятность/confidence — число от 0 до 1 (не строка с `%`, проценты считает frontend).
- Числовые измерения — отдельно `value` и `unit`.
- Геометрия — GeoJSON, координаты WGS84 в порядке `[longitude, latitude]`.
- Enum-значения — `snake_case`.
- Отсутствующее значение — `null` (не пустая строка и не `"-"`); пустой список — `[]`; boolean — `true`/`false` (не `0/1`, не `"да"/"нет"`).
- Каждая сущность содержит `updated_at`.
- Списки — **cursor-based pagination**, единый envelope:

```json
{
  "data": [],
  "meta": {
    "next_cursor": null,
    "total": 0,
    "generated_at": "2026-09-17T14:35:00+03:00",
    "data_version": "2026-09-17T14:34:42+03:00"
  }
}
```

## 6. Ключевые сущности и обязательные поля ответов

### 6.1 Объект (facility)

Помимо идентификаторов (`id`, `internal_code`, `external_code`, `display_name`) и адреса, backend обязан отдавать по каждому объекту в списке:

- `location` (GeoJSON Point + флаг `is_demo`, пока нет подтверждённой геометрии);
- `current_state` (текущее состояние — отдельно от прогноза);
- `forecast` (`risk_level`, `max_probability`, `active_count`, `earliest_window_start`);
- `incidents` (`open_count`, `critical_count`);
- `assets` (`collector_count`, `sensor_count`, `offline_sensor_count`);
- `data_health` (`freshness`, `last_event_at`, `coverage`);
- `priority_score` — отдельная величина ранжирования задач, не равная вероятности риска.

Важно: **текущее состояние, прогноз, подтверждённый инцидент и рабочий приоритет — четыре независимых поля**, их нельзя схлопывать в один `status`.

### 6.2 Иерархия объекта

- Узлы дерева: `id`, `parent_id`, `entity_type` (`building`/`collector`/`section`/`equipment`/`sensor`), `entity_id`, `display_name`, `path[]`, `children_count`, `sensor_count`, `attention_count`, `current_state`, `risk_level`, `has_children`.
- Иерархия должна быть настраиваемой на стороне backend (переменная глубина), а не жёстко 6-уровневой — frontend не должен зашивать структуру.
- Устаревшие/неизвестные каналы (в истории 12 627 ID каналов против 11 485 актуальных — см. исходные данные) должны возвращаться как отдельная явная категория, а не пропадать из ответа.

### 6.3 Датчик (sensor)

Обязательные поля: `channel_id`, `tag`, `sensor_type`, `system_type`, `facility_id`, `hierarchy_node_id`, `hierarchy_path[]`, `position` (либо `geo`, либо `plan.{image_id,x,y,level}` — нормализованные 0..1 координаты, если нет геопривязки), `current_reading` (`value`, `numeric_value`, `unit`, `measured_at`), `current_state`, `forecast_summary`, `data_health` (`freshness`, `quality`, `last_seen_at`), `maintenance_state`.

- Датчик без координат обязан оставаться доступным в списке (не исчезать), с признаком «нет геопривязки».
- Значения бывают числовые и текстовые (состояния вроде «Норма», «Неисправен», «Обесточен», «Затоплен») — backend должен различать `value_type: numeric | categorical` в ответе по временному ряду.

### 6.4 Временной ряд датчика

Два формата ответа в зависимости от `value_type`:

- **numeric**: `points[]` (`timestamp`, `value`, `state`, `quality`), `thresholds[]` (`kind`, `value`), `missing_intervals[]`.
- **categorical**: `intervals[]` (`from`, `to`, `value`, `state`).

Backend должен поддерживать параметр `granularity` для агрегации/даунсэмплинга — ресэмплинг длинных рядов должен делать backend, а не отдавать frontend сырой массив без ограничений (см. также раздел производительности).

### 6.5 Прогноз (risk)

Полная карточка прогноза обязана включать: `forecast_id`, `risk_type`, `target` (тип и ID сущности, `hierarchy_path`), `as_of`, `lead_min_hours`, `horizon_hours`, `prediction_window {start, end}`, `probability`, `threshold`, `risk_level`, `priority_score`, `decision_status`, `sla_due_at`, `data_health` (`freshness`, `freshness_seconds`, `coverage`, `unknown_features[]`), `model` (`name`, `version`, `generated_in_ms`), `top_factors[]` (3–5 факторов, каждый с человекочитаемым `label`/`explanation`, `value`, `baseline`, `unit`, `direction`, `contribution` — **не сырые SHAP-коды**), `recommendation` (`code`, `title`, `description`, `recommended_due_at`, `source`), `created_at`, `updated_at`.

- `probability` и `priority_score` — разные поля; сортировка очереди рисков по умолчанию: `priority_score desc, predicted_window_start asc`.
- Пороги (`threshold`) уровней риска (low/medium/high/critical) backend определяет и отдаёт — **frontend не решает самостоятельно**, что означает, например, 68%.

### 6.6 Решения по прогнозу и конкурентность

- `POST /risks/{id}/acknowledge|reject|defer`.
- `reject` требует `reason_code` (из справочника) и **обязателен** свободный комментарий при `reason_code = "other"`.
- Backend должен реализовать **optimistic concurrency**: запрос содержит `expected_version`; при несовпадении версии — `409 Conflict` с актуальным состоянием сущности в теле ответа, чтобы frontend мог обновить карточку и не потерять решение пользователя.
- Каждое решение фиксируется с пользователем и временем и остаётся в журнале с исходом (`acknowledged`/`rejected`/`deferred`), не удаляясь из истории.

### 6.7 События и инциденты

Поля: `event_type`, `source`, `facility_id`, `sensor_id`, `occurred_at`, `ingested_at`, `state`, `value`, `is_confirmed_incident`, `verification_result`, `resolved_at`, `related_risk_id`.

- Backend обязан различать «тревожное событие» и «подтверждённый инцидент» как разные состояния, связанные через `related_risk_id`/`is_confirmed_incident`.

### 6.8 Заявки (work orders)

- Создание черновика: `POST /work-orders` с `source_risk_id`, `facility_id`, `target_entity_type/id`, `work_type`, `priority`, `due_at`, `description`, `comment`, `mode: "draft"`.
- Ответ включает `id`, `display_number` (человекочитаемый номер, например `ЗН-2026-0042`), `status`, `created_by`, `created_at`, `version`.
- Статусы заявки: `draft, ready, assigned, in_progress, completed, cancelled, integration_error` — backend отвечает машинным кодом, русская подпись — на стороне frontend/справочника.
- **Важно**: пока нет реальной интеграции с внешней системой заявок (АРМ), backend не должен возвращать статус, эквивалентный «отправлено в АРМ» — только честный `draft`.

### 6.9 Состояние источников данных

`GET /system/source-health` — массив по каждому источнику (`smvu`, `maintenance_registry` и т.д.): `source`, `display_name`, `status` (`online/delayed/unavailable`), `last_success_at`, `delay_seconds`. Нужно для баннера свежести данных и построчных warning в UI.

## 7. Live updates

- Для MVP достаточно **polling каждые 30–60 секунд**.
- Если backend в дальнейшем предложит **SSE/WebSocket**, событие должно иметь минимальную форму:

```json
{ "event": "risk.updated", "entity_id": "risk_01J104", "version": 5, "occurred_at": "2026-09-17T14:40:00+03:00" }
```

- Стрим используется только как триггер к перезапросу сущности по ID — backend не обязан (и frontend не будет пытаться) собирать полное состояние только из потока событий.

## 8. Справочники и конфигурация, которые обязан отдавать backend

Frontend не должен хардкодить или размножать по файлам:

- типы датчиков;
- единицы измерения;
- текущие состояния (`normal, warning, alarm, fault, offline, maintenance, disabled, unknown`);
- типы риска и уровни риска (`low, medium, high, critical, unknown`) — **вместе с порогами**, которые их определяют;
- причины отклонения прогноза;
- типы работ;
- статусы заявки;
- параметры SLA;
- threshold по типам модели;
- границы свежести данных (`fresh, delayed, stale, unavailable` — конкретные тайминги, например «stale после 15 минут», должны приходить от backend/config, а не быть зашиты во frontend).

Рекомендуется отдавать это либо как отдельные REST-эндпоинты справочников, либо единым config bundle.

## 9. Коды ошибок

Backend обязан возвращать структурированную ошибку:

```json
{
  "error": {
    "code": "FACILITY_ACCESS_DENIED",
    "message": "Недостаточно прав для просмотра объекта",
    "trace_id": "tr_01JXYZ",
    "details": {},
    "retryable": false
  }
}
```

Обязательные к поддержке HTTP-коды и семантика:

| Код | Семантика |
|---|---|
| 400 | validation error |
| 401 | сессия истекла |
| 403 | доступ запрещён (в т.ч. попытка прямого доступа к чужому объекту — без утечки данных объекта в ответе) |
| 404 | объект не найден или скрыт (то же самое для несуществующих и недоступных — не различать в ответе) |
| 409 | конкурентное изменение (см. п. 6.6) |
| 422 | доменная валидация |
| 429 | слишком много запросов |
| 500 | внутренняя ошибка |
| 503 | источник данных или модель недоступны |

`trace_id` нужен для сквозной диагностики между frontend/backend.

## 10. Требования безопасности, относящиеся к backend

- Вся фильтрация по правам доступа — **только на сервере**; клиентское скрытие элементов не считается защитой.
- Поиск/автодополнение не должны возвращать недоступные пользователю объекты ни в каком виде (в т.ч. частичное совпадение).
- Общегородские агрегаты для диспетчера не должны допускать восстановление данных недоступных объектов (например, точных чисел по чужим площадкам).
- При отзыве прав в активной сессии — сервер должен немедленно инвалидировать доступ (а не только на следующий логин).
- Экспорт отчётов — отдельный permission (`report.export`), доступный руководителю всегда, диспетчеру — только по своему объекту.
- Все write-операции (`acknowledge`, `reject`, `defer`, создание заявки) должны сохранять audit-метаданные (пользователь, время) — соответствует требованию журналирования действий из общего ТЗ.
- Персональные данные и точные адреса — вопрос конфиденциальности, требующий отдельного решения (см. открытые вопросы, п. 11.4).

## 11. Производительность (то, что должен обеспечить backend)

- Server-side (cursor) pagination для всех списков.
- Даунсэмплинг временных рядов на backend (или в adapter-слое), а не передача сырых больших массивов на frontend.
- Время генерации прогноза попадает в ответ (`model.generated_in_ms`) — полезно для мониторинга SLA (пересекается с нормативом «inference ≤ 300 c» из общего ТЗ).
- Данные для карты должны поддерживать фильтрацию по `bbox`, чтобы не отдавать сразу весь город без необходимости.

- Финальные коды ошибок.
- Частота обновления данных / вариант доставки: SSE, WebSocket или только polling.
- Формат геометрии: GeoJSON с реальными координатами или внутренние планы (image + x/y)?
- Готовность к выдаче OpenAPI-спецификации.

## 13. Соответствие с основным отраслевым ТЗ

Данный API-контракт не противоречит [BACKEND_REQUIREMENTS.md](BACKEND_REQUIREMENTS.md), а конкретизирует его в части UI-слоя:

- горизонт прогноза ≥24 ч и inference ≤300 с — совпадает с общим ТЗ, добавляется поле `model.generated_in_ms` для наблюдаемости;
- источники СМВУ/ОДС/реестр оборудования — те же, что в общем ТЗ, здесь дополнительно зафиксирован read-only режим доступа и структура `source_health`;
- RBAC/LDAP/AD, TLS 1.2+, аудит-журнал — требования общего ТЗ, здесь детализированы в виде конкретных permission-строк и обязательного audit metadata на каждый write-запрос;
- добавляется то, чего не было в общем ТЗ явно: контракт REST API (эндпоинты, envelope, коды ошибок), optimistic concurrency через `expected_version`/409, модель live-updates (polling/SSE), необходимость backend-конфигурации порогов риска и границ свежести данных.

## 14. Уточнение организаторов: все внешние источники эмулируются

Ответ на вопрос об интеграциях (получен от организаторов после подачи вопроса о ТЗ):

> Система учёта заявок — это собственный help desk, разработанный на Django. Реальная интеграция с ней невозможна по соображениям безопасности. Все внешние взаимодействия необходимо реализовать через шаблоны и эмуляцию событий. Никакие реальные интеграции не предоставляются. При создании эмуляции следует использовать данные, которые выглядят адекватно и правдоподобно, а не просто случайные числа.

Практические следствия для backend, реализующего контракт из раздела 5–8 этого документа:

- **`POST /api/v1/work-orders`** и весь дальнейший жизненный цикл заявки (`draft → ready → assigned → in_progress → completed/cancelled`, статус `integration_error`) backend обслуживает **сам, локально** — реального вызова во внешний help desk нет и не будет. Статус `integration_error` при этом стоит сохранить в контракте намеренно: он показывает, что flow спроектирован с учётом будущей интеграции, даже если сейчас она замокана.
- Источники `smvu`, `ods_journal` (журналы ОДС), `equipment_registry` в ответе `GET /api/v1/system/source-health` тоже являются эмулируемыми провайдерами внутри самого backend, а не реальными подключениями — их `status`/`delay_seconds` должен генерировать сам сервис (например, детерминированно по сценарию демо), а не забирать из живой системы.
- Раздел 17.16 исходного документа («справочники не должен размножать frontend») и раздел 8 этого файла остаются в силе без изменений — просто источник данных для наполнения справочников и генерации потока событий теперь: подготовленный на бэкенде эмулятор, а не внешний API.
- Требование «данные должны выглядеть правдоподобно, а не как случайные числа» напрямую связано с критериями финальной экспертизы из общего ТЗ («проверка прогнозирования — оценка достоверности», «соответствие прогнозов реальному поведению инфраструктуры»): эмулятор нужно строить на реальных паттернах из выданного датасета (95 объектов, ~11.5 тыс. каналов, история сработок), а не на равномерном рандоме.
- Практически это означает, что модуль эмуляции внешних источников — не второстепенная заглушка, а часть основной архитектуры backend, которую стоит проектировать так же тщательно, как и сам API: с воспроизводимыми сценариями (ср. `16.4 Fixture сценарии` из frontend-ТЗ — 12–20 связанных сценариев), а не ad hoc моками под каждый эндпоинт отдельно.
