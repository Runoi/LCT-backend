# ТЗ backend: сервис прогнозирования инцидентов Москоллектора

Версия 1.0. Статус: для согласования командой.

## Назначение

Краткое рабочее ТЗ по backend-части проекта: что реализовать, чем, что уже есть, чего не хватает. **ML-моделирование, работа с датасетом для обучения и frontend — не предмет этого документа**, это отдельные зоны ответственности; здесь backend взаимодействует с ними только через контракты (API для фронта, интерфейс для модели).

Подробности и обоснования — в `BACKEND_MASTER_PLAN.md` и связанных файлах в этой папке; здесь — только выжимка для исполнения.

## 1. Границы backend-части

**Входит:**
- REST API по контракту для фронтенда (`/api/v1/*`).
- Хранилище (БД) и схема сущностей (объект → здание → коллектор → участок → датчик).
- Авторизация/RBAC (mock LDAP/AD, capability-модель прав).
- Слой эмуляции внешних систем: СМВУ, журналы ОДС, реестр оборудования, система заявок.
- Интеграционный интерфейс с ML-модулем — backend **потребляет** готовый прогноз (вероятность/горизонт/факторы), не обучает модель сам.
- Упаковка решения для сдачи (разворачиваемый пакет + инструкция).

**Не входит** (чужая зона ответственности, не трогаем):
- Обучение и выбор ML-модели, feature engineering по журналу событий.
- UI/UX и компоненты дашборда — см. фронтенд-ТЗ.
- Расширение/чистка исходных датасетов.

## 2. Что уже есть (зафиксировано)

- Датасет: 95 объектов, 11 485 каналов датчиков — справочник каналов обновлён и проверен (связь канал↔объект есть у 100% строк, все ссылки валидны), журнал событий 2019 → середина 2026 (~313 млн строк, потоковая обработка обязательна). В справочнике каналов встречаются переносы строк внутри кавычек — парсить настоящим CSV-парсером, не построчным сплитом.
- Реальных интеграций с СМВУ/ОДС/реестром/заявками/LDAP не будет — только mock, это официально подтверждено организаторами.
- Вычислительных ресурсов и тестовых стендов от организаторов не будет — разворачиваем всё сами.
- Координат объектов не будет никогда — карта на фронте схематическая, backend отдаёт условную/сгенерированную геометрию (GeoJSON) или нормализованные `x,y`.
- API-контракт для фронтенда уже полностью описан (`BACKEND_REQUIREMENTS_FROM_FRONTEND_TZ.md`) — реализуем по нему, не придумываем заново.
- Требований к конкретному стеку нет, но в исходном ТЗ уже жёстко заданы: Linux, PostgreSQL 12+, TLS 1.2+.

## 3. Что нужно сделать

### 3.1 REST API для фронтенда

Ключевые группы эндпоинтов (полная спецификация — в контракте фронта):

| Группа | Эндпоинты |
|---|---|
| Auth | `GET /api/v1/me` |
| Объекты | `GET /facilities`, `/facilities/{id}`, `/facilities/{id}/hierarchy`, `/facilities/{id}/layout` |
| Датчики | `GET /sensors`, `/sensors/{id}`, `/sensors/{id}/series` |
| Риски/прогнозы | `GET /risks`, `/risks/{id}`, `POST /risks/{id}/acknowledge|reject|defer` |
| События | `GET /events` |
| Заявки | `POST /work-orders`, `GET /work-orders` |
| Статус источников | `GET /system/source-health` |

Формат: JSON, cursor pagination, ISO 8601, snake_case enum, коды ошибок 400/401/403/404/409/422/429/500/503, optimistic concurrency через `expected_version` → 409.

### 3.2 Хранилище и схема данных

- Иерархия объект→здание→коллектор→участок→датчик — **настраиваемой глубины**, не хардкодить уровни.
- Разделение на оперативный контур / архив / аналитические витрины.
- ETL из `ext-journal-*.csv` в БД — потоково, без загрузки файлов целиком в память (файлы по 1–2.7 ГБ).

### 3.3 Авторизация и права

- Permission-строки (`facility.read.all`, `facility.read.assigned`, `risk.acknowledge`, `work_order.create_draft` и т.д.) + `scope` (`all_facilities` / `assigned_facilities: [...]`) — не хардкодить роли, отдавать фронту через `GET /me`.
- Вся фильтрация по доступу — **на backend**, включая поиск и агрегаты (фронт скрывает элементы, но не защищает данные).
- LDAP/AD — только mock-провайдер аутентификации.

### 3.4 Эмуляция внешних источников

Обязательный компонент архитектуры (не заглушка «на скорую руку»):
- СМВУ — near-real-time поток показаний датчиков.
- Журналы ОДС — история срабатываний.
- Реестр оборудования — статичный справочник.
- Система заявок — полный жизненный цикл черновика заявки (`draft → ready → assigned → in_progress → completed/cancelled`) backend ведёт сам, реальной внешней системы нет.

Требование к качеству эмуляции: данные должны быть **правдоподобными** (на основе реальных паттернов датасета — частоты, распределения по типам датчиков), а не случайным шумом — это прямо оценивается экспертами.

### 3.5 Интерфейс с ML-модулем

Backend не обучает модель, но должен определить и задокументировать стабильный интерфейс обмена с ней, минимум:
- вход: идентификатор канала/объекта + временной срез признаков;
- выход: `probability`, `prediction_window {start, end}`, `risk_level`, `top_factors[]` (человекочитаемые причины), `recommendation`.

Точный формат — согласовать с data science частью команды, но именно backend отвечает за то, чтобы этот выход корректно попадал в `/api/v1/risks` для фронта.

### 3.6 Упаковка и деплой

- Разворачиваемый пакет (Docker предпочтительно) + пошаговая инструкция по установке.
- Резервный публичный демо-стенд — не обязателен, но сильно рекомендован как страховка.

## 4. Технологии (рекомендация, не требование)

Жёстких ограничений нет, но заданы в исходном ТЗ как обязательные: **Linux**, **PostgreSQL 12+**, **TLS 1.2+**. Рекомендация по остальному стеку — Python 3.10+/FastAPI (быстро пишется, хорошо ложится на потоковую обработку CSV и REST-контракт), но финальный выбор — на команде.

## 5. Нефункциональные требования

| Параметр | Значение |
|---|---|
| Горизонт прогноза | ≥ 24 ч (можно иначе, если обосновано) |
| Inference на объект | ≤ 300 с |
| Задержка обработки потока | ≤ 300 с |
| Одновременные пользователи | ≥ 20 без деградации |
| Восстановление после сбоя | ≤ 4 ч |
| Шифрование | TLS 1.2+ |
| Права доступа | RBAC (permission + scope) |

## 6. Приоритет реализации

**P0 (обязательный минимум):**
1. ✅ Готово: обновлённый справочник каналов перекачан и проверен.
2. Схема БД + ETL из журнала событий.
3. Эмулятор внешних источников.
4. `/api/v1/*` по контракту фронта.
5. Auth/RBAC.
6. Интерфейс приёма прогноза от ML-модуля.
7. Пакет для сдачи + инструкция.

**P1 (если остаётся время):** SSE/live-updates вместо polling, техническая возможность дообучения модели без реализации самого процесса, публичный демо-стенд.

**P2:** доп. роль «группа реагирования», расширенная аналитика/экспорт, блокировка карточки инцидента за первым открывшим.

## 7. Чек-лист готовности к сдаче

- Все обязательные эндпоинты контракта реализованы и отвечают в заявленном формате.
- Права доступа фильтруются на backend, а не только скрываются на фронте.
- Эмуляция внешних источников работает на правдоподобных, не случайных данных.
- Пакет разворачивается по инструкции «с нуля» на чистой машине.
- Прогноз от ML-модуля корректно доходит до `/api/v1/risks` и виден на фронте.

## 8. Открытые вопросы (детали — в `BACKEND_MASTER_PLAN.md` §9)

- Обязательна ли платформа INDASTRICS как среда исполнения, или нет — влияет на то, оборачиваем мы свой API вокруг неё или пишем независимо.
- Финальный формат интерфейса с ML-модулем — согласовать с data science.
- Может ли один диспетчер быть назначен на несколько объектов (влияет на модель `scope`).
